How this hub works

The reference for the hub — written for the owner who wants to understand it and for the expert who wants to check it. Plain words on the working pages, precise words here. Numbers on this page are read from the code, not from memory; where the hub falls short, it says so.

In six sentences

Current access rule: Desk, Assets and Watch refresh a complete directory every 30 seconds, revoke missing people and fail closed when its request-start age reaches 60 seconds. Pushes are best effort. External IdP changes must first reach the Hub.

The hub is two canisters on your cloud engine: one keeps your company's people, the other serves this UI. People come from three places — typed in here, pushed by your HR or sign-in system (SCIM 2.0), or pulled from Okta — and the e-mail address is the identity. Every app you connect asks the hub who is signing in, receives only the slice of the directory you allow (lanes), and receives best-effort lock-out notifications; bundled apps also enforce the 60-second directory limit. People sign in with the key on their own device (a passkey) or, optionally, through your company's Okta or Google. A separate vault canister snapshots individual canisters for owner-triggered restore; recovery must be tested, and a kitchen canister installs and updates the apps from recipes through this console; platform setup and recovery still need an operator. Software not built for the hub (Grafana, GitLab, Nextcloud …) signs people in through it as an OpenID Connect provider.

Where people come from

Added here. Typed in under People (or CSV import), with the org profile (title, department, manager, location …) editable in the hub. Can be switched off under Sources once a sync is the single source of truth — enforced in the backend, not only hidden in the UI.
SCIM 2.0 push from a compatible SCIM client (validate your tenant’s operations): /scim/v2/Users and /Groups, bearer token (512-bit, generated here, shown once). Creates, updates and deactivations land in seconds; a SCIM DELETE deactivates and never deletes. Changing an existing userName is refused with HTTP 409; address migration is not implemented. Filter support is userName eq only; pagination is not implemented yet. Groups pushed this way are read-only in the hub while the token is active — revoke the token and they become ordinary groups.
Okta pull (optional, advanced). The hub reads the Okta directory itself (OAuth private_key_jwt, keys generated in-canister) on a schedule: default hourly, owner-configurable, can be off; the scheduler ticks every 5 minutes, so a due run starts within ≤ 5 min. Okta event hooks can deliver deactivations between scheduled runs; the hook is authenticated by a 256-bit secret in its URL path only (Okta's HMAC header is not verified).
A person may exist in several sources at once and is active if at least one source says so — unless a manual lock-out says otherwise.

Identity and roles

The lowercased e-mail address is the identity across all sources and all apps. Display names are never used to merge anything.
Three staff roles are held by people: owner (everything — sources, tokens, roles, backups), admin (people, groups, apps, branding, undoing lock-outs), helpdesk (lock-outs, invites, read-only otherwise). Every sign-in key linked to a person inherits the person's role; a locked-out person's keys lose it in the same moment. Connected apps receive the role (hubRole) if you grant them the roles lane. Roles are enforced per method in the canister, not in the UI.
Controllers are owners. Whoever controls the hub canister at the platform level (the identity that deployed it; the vault, once it is a co-controller) passes every owner check. When changing roles the hub refuses to demote the last owner (people and legacy key-level owners count, controllers do not, and a controller may override); deleting or locking out the last owner is not guarded yet.
First run. Until the hub is claimed, the first non-anonymous sign-in on its URL becomes the owner (name, e-mail, company). There is no deploy-time secret: the protection is that only the deployer knows the URL in that minute. Claim it right after deploying.

Passkeys and invites

Who a person is (the directory entry) is kept apart from how they sign in (their keys). A staff member (helpdesk or higher) mints a one-time invite link — 256-bit code, single use, valid 7 days, revocable, re-minting replaces the older one. The person opens it and signs in with a passkey created on their own device through Internet Identity; the resulting principal is linked to their entry. A person can hold several keys; admins can unlink any of them.
Passkeys are phishing-resistant by construction (origin-bound public-key credentials). Their principal is derived per web origin, so the hub pins its canonical origin (.well-known/ii-alternative-origins) — set a custom domain up before the first sign-ins; retrofitting orphans accounts.
Hub staff can link their own key to their directory entry from the menu switch; a key cannot link itself to a person who holds a higher role than the caller (no escalation through linking).

Company sign-in (optional)

OIDC authorization code + PKCE against Okta (SPA app, no secret) or Google (web client, secret stored write-only, shown masked except its last four characters). The code exchange happens inside the canister via an HTTPS outcall. Only ACTIVE people get a session: 512-bit token, 8 h, ends on logout. There is no admin-side "kill all sessions": a locked-out person's token is refused on every call instead, and expired records are pruned every 5 minutes.
Token validation: RS256 signature using replicated JWKS retrieval; exact issuer and single audience, expiry, issued-at, subject, nonce bound to PKCE and email_verified=true. Unverified email addresses are refused. Rate limit on the exchange: 300 attempts per 5 minutes for the whole hub (transient, resets on upgrade) — it protects the provider's quota, not seats.

Groups

Flat groups, a person in any number of them. Created here or pushed via SCIM (Okta "Push Groups", Entra group provisioning). Groups are the scoping primitive: who may use an app, and — inside the apps — queues, approvers, roles. Open a group to see where it has an effect: the hub lists its own access policies and asks every connected app (hub_usesGroup, 10 s timeout, apps without the method are skipped).

The sample company

Home can load 24 fictional people at example.com (departments, managers, one already locked out), three groups and two menu entries, and remove them again in one click. Honest limits: sample people are ordinary local entries — they do appear in the directory your connected apps receive and count on Home; they can not get an invite (the hub refuses), so nobody ever signs in as one. Remove the sample before real people arrive.

Connecting an app

Apps is one list — every hub app, every external app and every plain link — with four things per row: who may use it, what it may know, whether it is on the menu, and Edit. 🍢 Connect an app first asks what you are connecting. An app built for the hub: paste its backend canister id; the hub calls hub_ping and hub_manifest (name, version, the lanes it needs and wants), pins the needed lanes on the skewer, lets you grant more, choose who may use it and create the bound menu entry — one call at the end; apps without a manifest are connected by hand. Other software with OpenID Connect: pick the preset, paste the address (details). Just a link: name and address. Self-service alternative: a developer files a request from the menu; on approval the lanes come from the manifest. Both sides verify each other by canister principal — no shared secret, no API key. Edit opens one panel per app: who may use it, what it may know, on the menu (switch + address), technical (service id or client id, redirect URIs, secret, remove).

Lanes — what leaves the hub

Per app, enforced server-side on every read: identity (always: e-mail, first/last/display name, active flag, source name and source id) · profile · groups · roles · avatars · notify · push · ai.
The ai lane carries no people data at all: an app with it may fetch the company's AI key (hub_aiCredentials, Settings → AI) for its own calls to the vendor — one key for the suite, rotated in one place, usage counted per app. External (OpenID Connect) apps never get it.
The profile lane forwards a fixed whitelist only: title, department, division, organization, businessUnit, city, state, countryCode, entity, manager, managerName, employeeNumber, mobilePhone, primaryPhone, startDate. The hub stores every scalar field a source sends (cost center, birth date, phone extension …); only those fifteen ever leave it.
groups and roles ride along as pseudo-attributes (groups = "a;b", hubRole) only when granted. A per-person group lookup (groupsOf) is answered only for people inside the app's own population.
Apps connected before lanes existed have no lane record and are treated as "all lanes" for reads — but see the push note below.

Who may use it — and how sign-in works

One policy per app: everyone in the directory, or only selected groups, hub roles and people. It is applied on tickets, checkAccess, the directory the app receives, avatars, notifications, and which menu entries a person sees. Source scope and attribute filters remain as advanced knobs underneath.
Tickets. A click on a menu entry mints a one-time ticket — 90 seconds, single use, bound to the person and to the entry's app; only that app's backend can redeem it, canister-to-canister. Unbound (legacy) entries may be redeemed by any connected app. Logging out does not invalidate a ticket minted seconds before (the 90-second window applies). Open tickets are transient and vanish on a hub upgrade.
Live gate. Suite apps refresh their directory permission snapshot at least every 60 seconds and deny access when it expires. A Hub lock-out wins over every directory source; external OIDC apps may keep their own sessions.

Access governance — asking, lending, checking

Three things every auditor asks for, built on the access policy above so no second rule system exists (page: Access).
Asking. An app with a people-based rule that a person may not use appears on their menu under Not on your menu — ask for access. They say why and for how long; hub admins (owner/admin) get a notification and decide with a duration — approve creates a grant, deny carries a note. The person is told either way. Apps open to everyone need no request; apps outside a person's source scope are not offered.
Lending (temporary access). A grant puts a person on the app's people list, or into an editable group, and records who gave it, why and until when (4 h · 1 d · 7 d · 30 d · until taken away). Authorization stops honoring a grant at its deadline. The 5-minute tick then records expiry: the entry is removed again, the journal gets a line, the person a notification. Taking access away by hand ends it at once. Grants never touch groups pushed by SCIM.
Checking (access reviews). A review freezes, per chosen app, one line per rule entry: each named person, each group (with member count), each hub role — or the single line "everyone" for open apps. The app's owners (Apps → Edit → who answers for this app; up to five) get the lines in their menu and keep or remove each one; lines without an owner land with the hub admins on the Access page. Remove is effective at once: the entry leaves the app's rule (a person also loses a running grant) and the person is told. An "everyone" line can only be confirmed — restricting an open app is a policy change, made deliberately under Apps. A review closes itself when every line is decided, or an admin closes it early; the record stays and exports as CSV (spreadsheet-safe cells).
Not yet. Reviews of group membership (only of group → app assignments), manager-based reviewers, reminders before the due date, separation-of-duties rules, requests routed to app owners instead of admins. Kept small on purpose: the owner sees what the rule is, not a second copy of it.

Directory and lock-out delivery

Apps pull the scoped directory (connectorDirectory) on their own timer — the SDK example pulls every 15 minutes — and on unknown sign-ins. With the push lane the hub additionally pushes it into hub_upsert every 15 minutes, for directories up to 5 000 people; larger ones are pull-only. The push loop iterates apps with an explicit lane record — an app connected before lanes existed is pushed only after you saved its lanes once. Push failures are not journaled yet.
Lock-out is pushed to every connected app the moment it happens (hub_deactivate, one call per app, 30 s timeout) — best effort, no retry, not journaled. An app that was unreachable in that second learns of it on its next checkAccess or directory pull, which is why the SDK guide asks for both. Offboarding is one guided flow: lock out → unlink keys → hand over their work (apps that hold owned objects implement hub_ownedObjects / hub_reassign).

Notifications — the return lane

Apps never e-mail or DM people themselves; they call hub_notify (needs the notify lane; admins may call it for tests). The hub stores it in the person's inbox (the bell on the menu) and — if Slack delivery is switched on, a bot is configured and the person has not opted out — sends a Slack DM. Payload policy: title + deep link only — title ≤ 200 characters, https URL ≤ 500 — content stays behind the app's own sign-in.
Limits: 120 calls per 5 minutes per app; 200 stored notifications per person (oldest evicted); 90-day retention; a repeated dedupeKey within 48 h is silently dropped (the call still returns ok).

Sign-in for other apps (OpenID Connect provider) alpha

Software not built for the hub — Grafana, GitLab, Nextcloud, Outline, oauth2-proxy, most vendor tools with an "OpenID Connect" switch — can use the hub as its identity provider. Apps → Connect an app → Other software: pick the app (Grafana, GitLab, Nextcloud, Outline, oauth2-proxy or "other"), paste its address — the callback URI and the menu entry are prefilled, and after Connect the wizard shows the exact settings block to paste into that app. Provider values and signing keys live under Settings → Sign-in for other apps. Underneath: name, redirect URIs (exact match), server app (client secret, shown once, stored as a SHA-256 fingerprint) or browser app (no secret, PKCE mandatory), token signature RS256 (default — mandatory in the standard, accepted everywhere) or ES256. The client is an ordinary connector underneath: lanes decide which claims it receives (who signed in → sub, email, email_verified, name, given_name, family_name, preferred_username; job profile → title, department, division, organization, city, countryCode, managerName, employeeNumber; groups → groups; hub role → hub_role), the access policy decides who may sign in, and a lock-out refuses the code, the token and userinfo within seconds. Where it shows up: in the Apps list like every other app (type "other software"; Edit → Technical holds client id, redirect URIs, secret) and on the menu as "signed in" — opening the entry opens the app, whose login sends the person through the hub without a second prompt (consent once).
Flow. Authorization Code only (response_type=code), PKCE S256 supported and required for public clients. The app sends the browser to <issuer>/oidc/authorize (the backend forwards it to the sign-in view on the frontend); the person signs in with their passkey (or existing session), sees one consent card — which app, as whom, which lanes — and is sent back with a 32-byte single-use code bound to client, redirect URI, nonce, PKCE challenge and person, valid 60 s. The app's backend posts it to <issuer>/oidc/token (client_secret_basic, client_secret_post or none + code_verifier) and receives an id_token (15 min; iss, aud, iat, exp, auth_time, nonce, amr:["passkey"] + claims) and an opaque access token (1 h) for /oidc/userinfo. Discovery at <issuer>/.well-known/openid-configuration, keys at /oidc/jwks. All HTTP endpoints run as update calls (consensus, no certification gap); the token endpoint allows 600 successful exchanges per client per 5 minutes (what bounds signing work — secrets and codes are 256-bit, guessing is not the threat). Codes and access tokens are stored under their SHA-256, so a state dump holds no live credential; a code that arrives with a verifier although it was issued without a challenge is refused (PKCE-downgrade protection); the token endpoint refuses repeated parameters and mixed client authentication; the sign-in page refuses to work inside another site's frame (frame-ancestors 'none' + a runtime check), honours prompt=consent/login by always asking, and rejects prompt=none. Failed exchanges (wrong secret, unknown code, PKCE failure, foreign code) are journaled, throttled per client.
Keys. One RSA-2048 key and one P-256 key per hub, generated in-canister from IC randomness: the RSA key by a resumable prime search that runs in the background (≈ 60 candidates per slice, one to three minutes, once — see keys). Owners can rotate; the previous RSA key stays in the JWKS for 24 hours. The issuer is the backend canister's URL until an owner sets a custom domain under Settings → Sign-in for other apps → Addresses — set it before the first app, changing it later means reconfiguring every app.
Identity lifecycle. Email is the current identity key in bundled apps. Do not reassign a former employee’s address to a different person: app history can follow that address even after deleting the Hub entry. Use a distinct address until immutable person IDs and migration are implemented.
Subject. sub is an opaque random id allocated once per e-mail address — because the e-mail is the hub's identity. Consequence, stated plainly: an address re-issued to a new hire inherits the old subject at every app unless the old person was purged from the hub first (purging retires the subject); an e-mail change gives a new subject. amr says passkey for passkey sessions and fed for company-SSO sessions.
Not yet. No refresh tokens (apps re-authorise silently; passkey sessions make that a redirect without a prompt), no end_session_endpoint or back-channel logout — an app's own session lives as long as the app decides, the same limit Okta has —, max_age is ignored and prompt=login cannot force a fresh passkey (it asks for consent instead), no picture claim, no PS256/HS256, the ES256 key cannot be rotated yet, no dynamic client registration ever, no SAML ever. SCIM out (the hub provisioning people into other apps) is the planned second step.

The menu

What your people open: greeting, their entries (only the apps their policy allows, and only those switched on the menu), pins and recents, the bell, sign-out. The order is alphabetical for everyone — there is no admin-set order; people pin their own favourites ("Your favourites") and the menu remembers what they used recently. Each entry shows a picture if an admin set one (Apps → Edit → On the menu → Picture; scaled to 128 px, stored in the hub, no outside requests) — otherwise two letters from the name in a fixed colour. The same picture appears in the Apps list and on the sign-in card of external software. Three kinds of entry: a hub app (signs in by one-time ticket), other software (opens the app, which signs the person in through the hub), a link (opens a page). Reached with a passkey or a company SSO session — one person plane, two ways in. Hub staff flip to the same view with "Your team's menu ↗" after linking their own key, and open every app exactly as an employee would — real tickets, no test mode.

The vault

A separate canister that holds no business data — only its target list, schedules, snapshot notes and a journal. It takes canister snapshots of every canister you add as a target — the Backups page registers the hub's two canisters and every connected app automatically — keeps them on a schedule (daily at an hour you pick, or every N hours; keep 1–10, the platform maximum is 10 per canister) and restores them. It can do that only because you make it a co-controller of each canister — the Setup (IT) tab prints the exact commands; you keep your own controller.
Why a separate canister. Snapshots are a controller operation and the canister must be stopped for take and load. A canister cannot stop itself and carry on, and a hub → vault → stop(hub) chain would deadlock. So the browser talks to the vault directly; the vault asks the hub vaultAuth(principal) — only the configured vault may ask, only owners pass.
Who may operate it. Hub owners, checked live at the hub for every state change (reads use a 5-minute cache), plus the vault's own platform controllers, who bypass the hub check.

What a snapshot and a restore do

Every snapshot — manual or scheduled — and every restore runs stop → act → start: users hit a "canister is stopped" reply for a few seconds; the stop waits up to 300 s for the canister's open calls. A canister that was already stopped on purpose is left stopped; one that was running is started again — three attempts; if all fail the reply says so and names the CLI command (a stop that times out is cancelled by a start). Before taking, the vault trims to "keep" (deletes the oldest extras) and replaces the oldest atomically when full. A manual snapshot on a canister without a schedule uses keep = 5.
Restore replaces Wasm and memory with the snapshot — everything after that moment is gone. By default the vault first takes a safety snapshot of the current state (a checkbox you can untick); it verifies the target snapshot exists and never evicts it; one lock covers the whole operation. If the platform reply is lost, the result is flagged "MAY have happened" rather than guessed; failed takes are re-checked against the snapshot list before being reported. Restoring the hub backend also rolls back people, roles, apps and the vault link — re-enter the vault id under Setup if the snapshot predates it.
A recipe may ship a picture (kitchen/art/<id>.png): it shows on the kitchen card and becomes the app's menu picture after install. Limits: the vault cannot protect itself (it holds nothing worth restoring); snapshots stay inside the platform (no download yet, see roadmap); locks self-expire after 40 minutes; journal keeps 1 000 actions, shows the newest 200; a failed scheduled run is visible on Home and under Schedules but is not yet pushed as a notification.

The kitchen — installing and updating without a terminal

A second small canister, sibling of the vault. Its asset canister — the pantry — holds recipes: an app's backend module, its frontend files (the committed versions with placeholders), the asset-canister module, and a manifest (recipes/index.json, produced by kitchen/tools/pack-recipes.py from the repo). On Install the kitchen creates two canisters (controllers: yours, the kitchen, the vault), installs the backend (directly up to 1.9 MB, through the management canister's chunk store above), installs the asset canister and copies the frontend files in — patching placeholders such as the backend id and the hub URL — calls the app's setHub, registers it in the hub (kitchenConnect: exactly the lanes the app's manifest needs, everyone may use it, a bound menu entry), sets the console labels plus PUBLIC_CANISTER_ID:* and registers both canisters in the vault. A failed install leaves a "failed" record with "Remove leftovers" (stops and deletes the half-installed canisters). On Update it takes a vault snapshot (mandatory when a vault is configured), upgrades the backend keeping memory (wasm_memory_persistence = keep) and refreshes the frontend files, dropping stale encodings and keys. Up to date is decided by the running module hash versus the recipe's sha256, never by version strings. The hub itself can be updated the same way once the kitchen is a co-controller of the hub's two canisters (a one-time add-controller, Setup (IT) prints it). Apps deployed by hand are adopted: the kitchen checks it controls both canisters and that the backend's hub_ping equals the recipe id (services: the running module hash equals the recipe's).
Cooking a whole stack. A kitchen without a hub shows "Cook your hub" on its pantry page: sign in, enter the setup code, press Cook, and it creates the vault and the hub's two canisters from recipes, wires them (vault.setHub / setKitchen, hub.bootstrapWire), registers the hub in the vault with a default schedule (one backup a day at 03:00 UTC, keep 3 — the vault accepts this from the kitchen only where no schedule exists yet; owners change it under Backups → Schedules) and labels everything for the Console — thirteen visible steps. The hub is born protected: a 256-bit claim code is planted as its KEBAB_CLAIM_CODE environment variable at creation, before any code runs, manual Hub deployments also require a code or controller authorization; only the person who cooked sees the code (once, via a certified call) and the hub's claim form takes it from the URL fragment and scrubs it. Cooking requires the operator’s KEBAB_SETUP_CODE; there is no open first-hour window. After a reload the same login can recover its accepted job and claim link. Install = one icp deploy (or one uploaded bundle), everything else in the browser.
Who may cook. Owners, checked live at the hub (kitchenAuth) for every action; the kitchen's platform controllers bypass that. The kitchen is a controller of everything it installs — the second most privileged canister after the vault — and journals every job. One job at a time; progress is polled step by step from the UI, each step with its exact error text if it fails.
Honest limits. The kitchen itself is still deployed with the CLI (one command); the .icp bundle upload is experimental in icp-cli. Recipes travel with the kitchen deploy; there is no online catalogue yet. The kitchen cannot update itself. Trust model & accepted risks

Engine subnet nodes. The hub runs on your cloud engine, a dedicated Internet Computer subnet. All HTTPS outcalls — SSO token exchanges, the Okta directory pull, Slack DMs — run non-replicated (is_replicated=false), because auth codes and DM sends are single-use and would otherwise fire once per replica. Consequence: a malicious node on the engine could in principle forge an outcall response (a forged Okta pull could flip statuses, subject to the lock-out-wins rule). This is the platform trust base of everything on the engine, not specific to this app.
Canister state is readable by node operators of the engine subnet (standard IC property today). Everything in the table above is stored in clear inside the canister. Encrypting it with platform-derived keys (vetKD) is possible in principle but is not designed or scheduled; treat the engine's operator trust as your trust base.
ID token verification. Incoming Google/Okta SSO verifies RS256 against replicated provider JWKS, exact issuer and single audience, expiry/issued-at, subject, verified email and a nonce bound to the PKCE verifier. Test the actual tenant configuration before adoption.
Passkeys & origins. Principals are origin-bound; the canonical origin is pinned via .well-known/ii-alternative-origins. Internet Identity is a dependency for passkey sign-in (a public system canister, not a vendor server).
First setup. The operator configures a private one-time setup code with tools/setup-code.py. Without a configured code only the actual canister controller can initialize the backend. A public URL does not confer ownership.
Vault and kitchen are controllers. Both hold controller rights over the canisters they protect or install: whoever can call them as an owner can restore old state or install code. They accept only the configured hub's owners (vaultAuth, kitchenAuth) plus their own platform controllers, journal every action, and hold no business data — but they are the two canisters to guard most.
Claiming a cooked hub. The claim code is 256 bits from IC randomness, planted as a canister environment variable before the hub's code is installed, returned only to the cook's principal through an update call (certified), carried to the hub in the URL fragment (never sent to a server), scrubbed from the address bar on arrival, and consumed on the first successful claim. Job progress and the ids of a cooking stack are visible only to the cook and to controllers.

Hardening in place

· Roles enforced per method (owner / admin / helpdesk; helpdesk may lock out and invite, only admins may undo a lock-out — single or bulk); app-facing queries assert registered canister principals; user endpoints are session-token based; linking a key cannot escalate a role.
· Invites: single active code per person, single use, 7-day expiry, revocable; claiming requires a non-anonymous caller.
· ssoExchange: input size caps, https-only redirect URI, global rate limit (300 / 5 min).
· Sync reentrancy guard per connection, self-expiring; a lock-out arriving during a sync wins over that sync's stale data.
· Journal: denied sign-ins and admin actions (nearly all — a handful of toggles were added to the journal only in September 2026), admin-only.
· The frontend loads its crypto/agent bundle exclusively from its own asset canister — no CDN, no third-party script; the hub makes no third-party calls for decoration (the former price chart proxy is retired).
· SCIM: bearer-gated, every mutation journaled, Users and Groups, deactivations pushed to apps at once; stored attributes pass a denylist (password, schemas, id, meta, active, userName, groups, x509Certificates are never stored; everything else in the body is kept) — forwarding to apps stays whitelist-only.
· Backups: only the configured vault may ask vaultAuth, only owners pass it, every vault action journaled; restore takes a safety snapshot by default.
· The hub is read-only towards its identity sources (Okta, SCIM clients); its only outbound writes are Slack DMs and the OIDC code exchange. Deprovisioning flows one way (source → hub → apps).

What an upgrade does

Persistent state (people, groups, apps, sessions, invites, notifications, journal, keys, tokens) survives a backend upgrade; stable variables are append-only and moc --stable-compatible guards every deploy. Transient state is lost: open app tickets, sync guards, rate-limit windows, the Okta bearer cache. Timers re-arm automatically. Vault locks are persistent and self-expire after 40 minutes. Take a snapshot before every live upgrade — that is what the vault is for.

Would this save your company money?

Compare the capabilities you actually need and contracts you can cancel. The MIT licence has no kebab-stack seat fee. The engine, external APIs, migration and your team's operating time still cost money. No kebab-stack capacity or monthly cost benchmark is available yet.

Use total cost, not a seat-price headline

Monthly total = licences + engine infrastructure + external APIs + operating hours × hourly cost + migration cost spread over an agreed period. Use your provider quote and pilot measurements. Existing SaaS may remain cheaper when support, missing integrations and service levels matter.

What control means here

You can inspect the source, control canister upgrades and choose an engine configuration. ICP, gateways and any enabled identity/AI/chat providers remain dependencies. Node location is a deployment decision; replication is not end-to-end encryption. Vault snapshots remain on the platform and cover individual canisters. There is no atomic suite-wide or off-site backup.

What to try first

Use test people to run onboarding, a request with approval, a device assignment, offboarding, a Hub outage and restore. Bundled apps refresh permissions every 30 seconds and deny access when the complete directory lease reaches 60 seconds. Upstream sync delay and external OIDC sessions have separate limits. Device trust, outbound SCIM and full external backups remain gaps.

State: alpha, in motion

The stack is alpha and has no production-user validation established for this review. This list is maintained with every release; if something you need is here, it is not done.

Known gaps

· One person, one row. The store is keyed per source record; the same human can appear twice in People (e.g. added here + SCIM). Access already merges by e-mail; the list view does not yet.
· No admin-side session revocation for company SSO (lock-out refuses the token instead).
· Lock-out push is best effort — no retry, not journaled; apps must keep re-checking (the SDK does).
· Push failures not journaled; legacy apps need their lanes saved once before they are pushed.
· Sign-in for other apps (OpenID Connect): no refresh tokens, no back-channel logout, no picture claim, ES256 key not rotatable, no SCIM out (provisioning people into those apps) yet, never SAML.
· SCIM: no pagination, only userName eq filtering, no externalId echo, unsafe userName/email renames are refused because email-keyed state cannot yet migrate atomically.
· Journal: capped, admin actions and activity mixed, no export, no paging.
· Directory scans are O(n); capacity and latency have not been benchmarked; measure the intended workload.
· SSO: local signature/claim regressions pass; actual tenant and relying-party interoperability still need a disposable-engine pilot. Public HTTP abuse controls and durable notification retries remain limited.
· No encryption of canister state beyond the platform; vetKD not designed.
· Vault: no snapshot download, failed schedules do not notify, cannot protect itself.
· First install needs the CLI: tools, build, deploy and private setup-code generation. Keep controller access for recovery and Kitchen upgrades. Hand-deployed stacks still wire the kitchen by hand (add-controller).

The connector contract in four lines

Every hub app implements three methods; the hub is their only caller and both sides verify each other by canister principal — no shared secret. The hub pushes hub_deactivate the moment someone is locked out; apps additionally gate every session with checkAccess. The full playbook (manifest, tickets, directory cache, notifications, ownership hand-over) is onboard-app.md above.
// implemented by each app's backend type ConnectorUser = record { email : text; displayName : text; firstName : text; lastName : text; active : bool; source : text; externalId : text; attributes : vec record { text; text } }; service Connector : { hub_upsert : (vec ConnectorUser) -> (nat); hub_deactivate : (vec text) -> (nat); // e-mails hub_ping : () -> (text) query; // returns the recipe id for the kitchen hub_manifest : () -> (record { name : text; version : text; needs : vec text; wants : vec text }) query; } // provided by the hub — call on login and on every session check: checkAccess : (email : text) -> (variant { active; inactive; unknown }) query

How it stays current

          

          The SDK lives in the same repository as the hub (sdk/) and is released with it. Two checks run before every hub deploy (hub/test/run-smoke.sh): sdk/tools/check-sdk.py compares every hub method the SDK promises with the hub's live Candid — name, arity, query vs. update — and refuses a deploy whose served /sdk/ copies differ from the sources; hub/tools/sync-sdk.py refreshes those copies and stamps /sdk/VERSION. Contract changes are additive: methods are never renamed or removed, new ones are optional for apps.

          Cookable apps. Four conventions make an app installable from the Kitchen page: hub_ping() returns the recipe id, setHub(Text) is controller-gated, the backend takes no init argument, dist/ carries the placeholders __BACKEND_CANISTER_ID__ / __HUB_URL__. Then one entry in kitchen/tools/pack-recipes.py — onboard-app.md § 10 has the table.

          The live contract (Candid) is above; the onboarding playbook is onboard-app.md in the table. Deploy discipline for every layer: moc --stable-compatible against the committed .most, a vault snapshot, then icp deploy. Stable variables are append-only; never --mode reinstall a live canister.
