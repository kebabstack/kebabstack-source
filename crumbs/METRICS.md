# Metric contract, version 2

All event times and API ranges are integer Unix seconds. `from` is inclusive, `until` exclusive. Daily buckets follow the website's time zone when the client supplies `dayStarts` (the UTC instants of local midnights, as the Crumbs app does); without it, and for hourly/minute buckets, UTC applies. Native reports span at most 1827 days. Query methods scan at most 50,000 retained events, including same-day session context before `from`. Dashboard and shared reports automatically retry scan-capacity or query-instruction failures through the corresponding `*Full` update method. Native REST uses that update path directly; the optional collector retries queries in the same way. Full methods use a 131,072-event bound derived from the existing 256 MiB storage charge and its minimum 2,048 bytes per event, so the scan cap covers the currently storable dataset. They perform the same exact calculation atomically, without sampling or summing daily uniques. Update execution takes longer and remains subject to platform instruction limits; storage, response sizes and workload cardinality remain finite. List limits truncate breakdown rows only (`truncated`); totals include all qualifying events. See TESTING.md for the measured workload, not a production throughput guarantee.

| Metric | Definition |
|---|---|
| Visitors | Distinct site-specific identifiers in selected events: daily cookieless estimates and c:-prefixed consented browser IDs. Cookie IDs can span days; neither is an identified person. Mixed-mode totals do not merge a browser across modes. Summing daily rows can overcount a cookie browser. NAT, changing IP/UA and privacy blocking affect accuracy. |
| Visits | Sessions with a qualifying pageview or custom event, ending after 30 minutes without either. Cookieless IDs rotate at UTC midnight; visits in both modes are split at UTC midnight even when daily buckets use another time zone. |
| Pageviews / events | Accepted pageview / custom-event records after deduplication. Engagement records increment neither. |
| Bounces | Visits with at most one pageview and no interactive custom event. A custom-only noninteractive visit can be a bounce. |
| Bounce rate | `100 * bounces / visits`, zero if no visits. |
| Duration | Sum of last minus first pageview/custom-event timestamp per qualifying session. Single-event sessions have zero duration. Divide by visits for the mean. Sessions are reconstructed through the report end, without future lookahead. |
| Engagement | Active visible-page milliseconds reported by the tracker. Engagement does not start or extend a session. |
| Scroll | Maximum observed depth per visit/path. Mean depth = scrollDepthSum / scrollSamples. Only pages with engagement measurements contribute. |
| Revenue | Sum of integer minor units grouped by currency. No FX conversion or guessed decimal multiplier; caller supplies currency-specific minor units. |
| Realtime | Distinct visitor estimates with a pageview in the preceding five minutes, not a presence connection. |
| Conversions | Distinct estimates meeting the goal filter; rate uses all qualifying visitors as denominator. |
| Funnels | Ordered steps within a session; each step counts distinct visitor estimates reaching that stage. Each event advances at most one step. |
| Journeys | Counts of observed pageview transitions per session, plus entry/exit markers. Filtered paths form the displayed sequence. |

Filters combine dimensions with AND, values within one dimension with OR; `exclude` negates the dimension match. Events are ordered by timestamp and backend-assigned native order (or signed collector insertion order), then ID. Site/source/medium/campaign/content/term acquisition comes from the first session event; subsequent SPA pageviews retain it. Entry/exit filters use the session's first/last pageview in loaded context. Other dimensions apply to each event. Filtered bounce and duration describe the full reconstructed qualifying session, not a made-up sub-session.

Page/source/device breakdown visitors are not additive: a visitor can appear in several rows. Properties must be allowlisted per site; use `prop:NAME` through the API. The simple browser/OS parser groups coarse families, not exact Plausible UA classifications. Referrer sources use hostnames (for example `www.google.com`), not Plausible's curated marketing labels.

Imported CSV rows retain the source's dimension grouping and integer counts. Missing source metrics are represented by zero in the transport model but are **unavailable**, not measured zeros. `import:visitors` is the only complete daily visitor total; never sum visitors across pages, custom-event properties, source groups or browser versions to manufacture a total. History does not support reconstructed sessions, funnels, arbitrary intersections or automatic merging with native traffic. Importer accepts UTC exports only; choose non-overlapping source periods.

Native ingress timestamps the first successful receipt, not a browser-provided clock. Same-ID retries retain their original time/order/visitor, including after midnight, while retained and within the seven-day ingestion window. Native location/network fields use a current operator-loaded dataset when matched. Existing events, missing matches and expired datasets remain unknown; browser screen size and automation signals are untrusted measurements. See TRAFFIC.md. Daily secrets differ between native and Node collectors; use one collector transport per website, and record a mode switch as a measurement boundary.

## Acquisition, goals and combined reports (0.6.0)

- Channels and AI assistants use the first recorded event of each 30-minute visit. Explicit campaign medium labels take precedence over recognized referral hosts. Host matching requires an exact hostname or subdomain boundary. Missing referrers remain unknown; AI referrals measure clicks from recognized assistants, not crawler activity or all AI influence. UTM labels are sender-controlled inputs.
- Page and event goal completions count matching records. Scroll goals require a matching page and an engagement record at or above 1–100%; at most one completion per visit per goal. A visitor can complete an event goal repeatedly; conversion rate uses distinct visitor estimates divided by the report's visitor estimates, not completion count. Engagement is sent every 30 visible seconds and at page lifecycle boundaries, best effort.
- Revenue is attached to recorded events in minor currency units. Acquisition attribution is visit-first; currencies are never converted or summed together. Revenue tables have up to 1,000 traffic-ranked groups and state when low-volume groups may be omitted; totals cover the entire valid query. This is not an accounting ledger, refund system or proof of payment. Send once after confirmed success with a stable, non-personal event ID for delivery retries.
- All websites sums each permitted site's report. Visitor counts are site-specific estimates (daily in cookieless mode), not unique people across websites. A failed site is identified; partial totals are labelled. Site-specific filters are intentionally absent in the combined view.
- Realtime uses a rolling 30-minute window with UTC minute buckets; the separate active indicator covers five minutes. Auto-refresh is 30 seconds while the page is active, with draft preservation. Normal reports use UTC hours/days. Missing buckets mean no recorded events, not confirmed uptime of collection.
- Saved filters and funnels store configuration, not metric snapshots. They are shared with the website's readers and managed by website managers/admins, capped at 100/site, 2,000/deployment and 8,192 filter-value characters per saved item.
- Search Console stores the latest explicitly refreshed report. Google uses Pacific Time, finalized data, privacy omissions and top-row limits. Its clicks are not Crumbs visitors. The saved snapshot states its own dates, ignores Crumbs filters and records refresh time. Totals are queried separately, never reconstructed by summing incomplete search terms.
- Retention can be configured up to 1,827 days (roughly five years), still subject to event/storage/report bounds. Raising retention neither restores deleted data nor provides rollups or five-year capacity at arbitrary traffic volume. Default remains 365 days.

## Optional consented cookies (0.9.0)

`trackingMode` groups/filters `cookieless` and `cookie`. Cookie input is a random UUID and an explicit consent flag; the public endpoint cannot independently prove the visitor consented. Both collectors derive the same site-scoped cookie pseudonym with a domain-separated hash; it is not an authentication credential. Cookie mode permits unique browser estimates across days (within expiry/retention), avoiding IP/UA merging on shared networks. Switching modes can count the same browser twice; do not merge the groups into identified people. Sessions still split at UTC midnight and after 30 minutes without a pageview/custom event. Returning/new visitor cohorts are not shipped.

A SPA path or query change counts even when its sanitized stored path equals the previous one. Replacing history with the identical route, fragment-only changes without explicit hash routing, or repeated consent callbacks do not create extra pageviews. BFCache restoration counts a fresh pageview. `pageview()` is deduplicated for the current route; document reloads count anew. Privacy signals and consent govern all collection. No historic events or totals are rewritten by this release.

## Traffic context and imported Matomo data (0.11.0)

Traffic classification is automation-signal (browser webdriver flag), hosting-network (known range match), unclassified (no such evidence), or unknown (older events). None proves a human or bot. Screen and network are event dimensions, not visitor identity inputs. Matomo History stores original date labels and source timezone, available metrics and original metric names. It is not merged into native totals; unavailable fields are not measured zeros.

## Faster overview reports (0.13.0)

The overview and shared report bundle their dimensions for the same interval. Events and sessions are prepared once and whole-period totals reused; visitors are never calculated by summing daily uniques. Each bundle reads one current snapshot, checks access again, and uses no persistent result cache. Current, previous and realtime intervals remain separate snapshots as before. The previous period and realtime may therefore reflect a slightly different collection instant.

Direct Candid clients can call `reportBundle(token, request, [(dimension, limit)])`, falling back to `reportBundleFull` only for a query capacity/instruction error. Results are in input order and use the same `Report` records and counting/filter rules as individual reports. All dimensions share the request’s site, interval, filters and local-midnight boundaries; each has its own row limit. Bounds: 1–8 dimensions, each limit 1–1,000, at most 2,000 requested rows total. Invalid bundles fail as a whole. These are Candid-only dashboard methods; existing REST/OpenAPI/SDK and MCP report contracts remain unchanged. Intervals over 900 days retain the existing segmented chart path. No reimport or tracker change is needed.

A bundle is limited to 200,000 scanned-event × dimension units before aggregation. If a bundle exceeds this work limit or the full execution budget, the shared browser client splits **dimensions**, never the date range or visitor population, and only displays the complete result. Split groups are individually authorized snapshots and may reflect intervening collection. An individual report failure remains visible. Visitor counting uses an exact sparse bitmap over local ordinals, not a probabilistic estimate; visit counts use contiguous session traversal.
